# v2.0.7 — Independent updater bootstrap

## Decision

Starting with v2.0.7, the application no longer generates the installer helper
from the Python source that happens to be running. The signed public release
contains a versioned bootstrap asset:

`TikTokAffiliateUpdater-v1.0.0.ps1`

`stable.json` keeps schema `tiktok-affiliate-report.update.v1` for compatibility
with v2.0.6 and adds a signed `bootstrap` object containing `protocol`, `name`,
`url`, `size`, and `sha256`. Older clients ignore the extra field and continue
to install the target with their legacy helper. v2.0.7 and later download both
assets, verify both against the signed manifest, and execute the downloaded
bootstrap from the versioned data directory.

## Why a signed PowerShell asset

- It reuses Windows PowerShell 5.1 already required by the current updater.
- It adds no runtime dependency and no second large PyInstaller distribution.
- The script is independently replaceable in every release without copying
  complex install/restart logic from the source application.
- Authenticity comes from the existing pinned Ed25519 manifest signature; the
  bootstrap SHA-256, size, protocol, filename, and HTTPS URL are covered by the
  signed bytes.
- The bootstrap runs from `{app}\data\updates\v<target>`, which Inno Setup never
  deletes or overwrites while the process is running.

## Trust and execution boundary

1. The app downloads `stable.json` and `stable.json.sig` without credentials.
2. It verifies the exact manifest bytes with a pinned Ed25519 public key.
3. It validates the installer and bootstrap metadata against strict allowlists.
4. It downloads each asset to a temporary file, enforces its size limit, checks
   SHA-256, and only then atomically moves it into the target directory.
5. Immediately before launch it rechecks both local hashes and filenames.
6. The bootstrap has no network responsibility. It rechecks installer size and
   SHA-256, writes the existing atomic status protocol, waits for app exit,
   invokes Inno Setup, restarts the app, and waits for `/health`.
7. The app only shuts down after a matching `waiting_for_exit` handshake.

The release workflow mirrors and anonymously re-downloads exactly five assets:
installer, bootstrap, `SHA256SUMS.txt`, `stable.json`, and `stable.json.sig`.
Both executable assets must match their signed manifest metadata and checksum
entries before the release or public feed can be promoted.

## Compatibility boundary

The v2.0.6 → v2.0.7 transition is still executed by the helper already shipped
in v2.0.6. Therefore v2.0.7 deliberately preserves feed schema v1, the pinned
key, installer name, AppId, install path, data directory, silent Inno flags,
root executable, `instance.json`, `/health`, and `--updated` restart behavior.

A v2.0.6 client can skip v2.0.7 because the public feed is a single latest
manifest. Later installers must remain compatible with the v2.0.6 legacy helper
until a separately approved staged-feed migration retires that compatibility.
After any client has installed v2.0.7 or later, subsequent transitions use the
signed independent bootstrap asset. Clients accept newer semantic bootstrap
versions while protocol `1` remains compatible, so bootstrap fixes do not
depend on the source version currently installed.

## Protocol v1

The application launches `TikTokAffiliateUpdater-v1.0.0.ps1` with the existing
arguments plus `BootstrapProtocol=1`. The bootstrap rejects any other value.
Protocol v1 preserves:

- status schema `tiktok-affiliate-report.update-status.v1`;
- phases `waiting_for_exit`, `installing`, `restarting`, `installed`, `failed`;
- atomic status-file replacement;
- 120-second parent exit wait;
- 15-second executable unlock wait;
- installer size and SHA-256 revalidation;
- 90-second relaunch health wait;
- one restart attempt after a failure that occurs before the target app was launched.

Protocol v1 does not keep a last-known-good installer and therefore does not
promise binary rollback after Inno Setup has replaced the application. A future
LKG rollback design requires its own storage, retention, status and recovery
contract; v2.0.7 fixes bootstrap ownership without claiming that capability.

Breaking CLI or status changes require a new bootstrap protocol and an explicit
bridge strategy. Compatible implementation fixes increment the bootstrap asset
version while remaining on protocol v1; every signed release supplies and
authenticates the exact bootstrap bytes selected for that update.

## Release gates

- Python manifest/download/launch tests reject missing, malformed, oversized,
  tampered, or unsupported bootstrap assets.
- Windows tests parse and execute the real checked-in PowerShell bootstrap and
  prove the handshake before app shutdown.
- Candidate artifact allowlists and SHA256SUMS cover installer plus bootstrap.
- Fresh and direct-upgrade installer smoke pass on the exact candidate SHA.
- The tag commit has a successful exact-SHA post-merge Windows smoke.
- Signed private/public drafts are anonymously downloaded and reverified before
  feed promotion.
- After public release, the real UI updater is run repeatedly from v2.0.6 to
  v2.0.7; each run must observe disconnect, reconnect, installed v2.0.7, and
  preserved marker data. Failures remain visible and are not averaged away.
